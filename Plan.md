# Skill Version History Implementation Plan

## Goal

Complete the ADR-0008 feature loop by adding Skill Version History and Skill Version Labels on top of the append-only Skill Version DAG.

The product model follows Google Docs named versions and Obsidian file recovery:

- Every durable Skill edit creates a Skill Version.
- Version History lists historical Skill Versions for review and recovery.
- A Skill Version Label is an editable human label attached to one Skill Version.
- Labelled Skill Versions are retained permanently.
- Restore copies a historical Skill Version into a new current head version.

## Confirmed Decisions

### Product language

Use these user-facing terms:

- **Skill Version**: a saved historical state of one Managed Skill.
- **Skill Version History**: the edit history timeline for one Managed Skill.
- **Skill Version Label**: an editable human label on one Skill Version.
- **Skill Primary Key**: the internal storage key for Skill domain relationships.

Avoid exposing snapshot/tag vocabulary in new product UI or API contracts.

### Storage naming

Apply `pk`/`id` naming inside Skill domain tables only:

- `pk`: internal integer primary key used for SQLite/D1 relationships.
- `id`: externally exposed opaque ID used by REST JSON and frontend state.
- Foreign keys use `*_pk`, for example `skill_pk`, `version_pk`, `parent_pk`.

Better Auth and OAuth tables keep their current naming.

### MCP boundary

MCP remains a current-state Skill Delivery and authoring surface:

- `list_skills`
- `read_skill`
- `create_skill`
- `update_skill`

Version History, Version Labels, historical resource reads, and restore are REST/UI management features.

### REST/UI behavior

- Version History list is sorted newest first.
- Version list item shape is minimal:

```ts
{
  id: string;
  createdAt: string;
  label: string | null;
}
```

- Skill detail current-state response stays focused on current Skill state.
- Historical Version IDs appear through Version History management routes.
- Each Skill Version has at most one label.
- Label text must be non-empty after trimming.
- Clearing a label uses the explicit DELETE endpoint.
- Restore requires confirmation in the UI.
- Restore creates a new head version copied from the selected historical version.

## Data Model

### `skills`

```sql
skills(
  pk INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  owner_user_id TEXT NOT NULL,
  head_version_pk INTEGER NOT NULL REFERENCES skill_versions(pk),
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  UNIQUE(owner_user_id, name)
)
```

### `skill_versions`

```sql
skill_versions(
  pk INTEGER PRIMARY KEY,
  id TEXT NOT NULL UNIQUE,
  skill_pk INTEGER NOT NULL REFERENCES skills(pk),
  parent_pk INTEGER REFERENCES skill_versions(pk),
  description TEXT NOT NULL,
  license TEXT,
  compatibility TEXT,
  allowed_tools TEXT,
  metadata TEXT,
  origin TEXT,
  created_at INTEGER NOT NULL
)
```

ID format recommendation: cuid2 string generated by `@paralleldrive/cuid2`, with no type prefix.

### `skill_version_resources`

```sql
skill_version_resources(
  version_pk INTEGER NOT NULL REFERENCES skill_versions(pk),
  path TEXT NOT NULL,
  sha256 TEXT NOT NULL,
  media_type TEXT NOT NULL,
  size INTEGER NOT NULL,
  created_at INTEGER NOT NULL,
  UNIQUE(version_pk, path)
)
```

### `skill_version_labels`

```sql
skill_version_labels(
  pk INTEGER PRIMARY KEY,
  id TEXT NOT NULL UNIQUE,
  skill_pk INTEGER NOT NULL REFERENCES skills(pk),
  version_pk INTEGER NOT NULL REFERENCES skill_versions(pk),
  label TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  UNIQUE(skill_pk, version_pk)
)
```

ID format recommendation: cuid2 string generated by `@paralleldrive/cuid2`, with no type prefix.

## REST API Plan

### List versions

```http
GET /api/v1/skills/:skillName/versions
```

Response:

```ts
{
  versions: Array<{
    id: string;
    createdAt: string;
    label: string | null;
  }>;
}
```

### Read a version

```http
GET /api/v1/skills/:skillName/versions/:versionId
```

`versionId` accepts an opaque cuid2 ID or the reserved selector `current`.

Response should mirror the current Skill detail shape where practical, while representing the selected historical version.

### Read a version resource

```http
GET /api/v1/skills/:skillName/versions/:versionId/resources/raw?path=:path
```

`versionId` accepts an opaque cuid2 ID or `current`.

### Set or edit a label

```http
PUT /api/v1/skills/:skillName/versions/:versionId/label
Content-Type: application/json

{
  "label": "Known good"
}
```

`versionId` accepts an opaque cuid2 ID or `current`.

Behavior:

- Trim label input.
- Reject empty labels with validation error.
- Upsert the single label for that Skill Version.
- Return the updated label.

### Delete a label

```http
DELETE /api/v1/skills/:skillName/versions/:versionId/label
```

`versionId` accepts an opaque cuid2 ID or `current`.

Behavior:

- Delete the label for that Skill Version when present.
- Treat missing label as idempotent success or 404; choose one during implementation based on existing route conventions.

Recommendation: idempotent success for easier UI behavior.

### Restore a version

```http
POST /api/v1/skills/:skillName/versions/:versionId/restore
```

Behavior:

- `versionId` must be an opaque historical Version ID.
- Reject `current` with a validation error.
- Copy the selected version metadata and full resource manifest into a new Skill Version.
- Set the new Skill Version as current head.
- Return current Skill detail.

## Risks and Mitigations

### Migration drift

The current branch has already used an older 0003 migration locally. Mitigation: delete and regenerate 0003 after final schema stabilization, then reset local D1 state for verification.

### API surface creep

Version History belongs to REST/UI management. MCP stays current-state focused.

### Identifier confusion

Use `pk` for internal storage keys and `id` for opaque public identifiers inside Skill domain code. Keep conversion at repository/service boundaries explicit.

### Restore semantics

Restore must create a new head version. It should record a normal append-only edit so history remains linear for user review.
